# weave：让 Go 的并发 bug 无处可藏

## 一个让人头秃的场景

你写了段并发代码，本地跑一万遍都对，测试全绿，上线。三周后凌晨两点，线上崩了一次。你复现不出来，加了日志，又跑一万遍——还是好的。于是这个 bug 就成了团队传说，谁也不敢碰那段代码。

这类 bug 有个共同点：**它只在某一种特定的 goroutine 交错顺序下才出现**。而 goroutine 谁先谁后，是由调度器决定的，带着随机性。你的测试跑一万遍，可能一万遍都恰好避开了那个"要命的顺序"。

`go test -race` 能帮上一部分忙，但它是个**旁观者**：它只观察"这一次实际发生的执行"，看有没有漏加锁的内存竞争。如果那个致命交错这次没跑出来，它也一样沉默。它能不能抓到 bug，本质上还是**看运气**。

weave 换了个思路：**与其祈祷撞上那个坏顺序，不如把所有顺序都系统地跑一遍。**

> 名字的来历：goroutine 就像一根根线，一种调度顺序就是一种"织法"。weave（编织）做的事，就是把这些线所有可能的织法都编一遍，看哪一种会织出破洞。

## 核心思路：接管调度器

平时 Go 的调度器是"多路并行"的——多个 P 上真的有多个 goroutine 在同时跑，顺序你说了不算。weave 做了两件"反直觉"的事：

1. **串行化**：同一时刻只让一个 goroutine 跑。把并行变成"一步一步来"。
2. **枚举**：把同一个测试反复跑很多遍，每一遍在关键的"岔路口"故意选一个不同的走法，直到把所有本质不同的走法都覆盖。

只要任何一遍跑出了 panic、死锁、断言失败，weave 就抓住了它——并且告诉你**是哪条路径**，还给你一颗"种子"让你确定性地重放。

要实现这套，动了三个地方：编译器、运行时、testing 库。下面一层层说。

---

## 改动一：编译器——把内存访问变成"可暂停的点"

先想一个问题：weave 要在"关键岔路口"切换 goroutine，那**哪里算岔路口**？

对于 channel 收发、加锁解锁，标准库在这些原语内部埋了轻量的钩子（而且它们阻塞时本来就会经过运行时），所以 weave 天生看得见。但对于最朴素的一句 `x = x + 1` 呢？这只是一次内存读、一次内存写，CPU 眼里平平无奇，运行时根本看不见。可偏偏最经典的并发 bug（丢更新）就藏在这种普通读写里。

解决办法跟 `-race` 一模一样：**让编译器在每次内存读写前，偷偷插一个函数调用**。

- `-race` 插的是 `raceread` / `racewrite`（记录一下，供竞争检测用）。
- `-weave` 插的是 `weaveread` / `weavewrite`（把这里变成一个可以切换 goroutine 的调度点）。

关键在于：**这两者插桩的位置完全相同**，所以 weave 直接复用了 race 那条现成的插桩流水线（`cmd/compile` 里的 `instrument2`），只是在最后一步换成调用自己的钩子。

复用带来一个白捡的好处——**逃逸分析剪枝**。编译器早就知道哪些变量是"只有当前 goroutine 能碰到的局部变量"（没有逃逸到堆上）。这些变量不可能引发并发问题，race 本来就不给它们插桩，weave 顺理成章也跳过。结果就是：weave 只在**真正共享**的内存上设岔路口，状态空间小了一大圈。

用起来就一个 flag：

```
go test -weave
```

这里有个和 `-race` 不同的细节：`-race` 会插桩包括标准库在内的**所有依赖**，而 `-weave` 只给你**命令行上指定的包**（通常就是被测包）的内存读写插桩——范围更小、更省，因为有意思的共享内存 bug 基本都在你自己的代码里。（另注：channel/mutex 测试连这个 flag 都不用加，那些钩子在标准库里常驻；只有要探查普通变量上的数据竞争时才需要。）

几个边界这里顺带交代：
- **运行时自己不插桩**，否则 `weaveread` 会递归调用回自己。
- **`-weave` 和 `-race` / `-msan` / `-asan` 互斥**——它们抢同一条插桩流水线，硬凑到一起会让 weave 被悄悄丢掉，所以直接报错拦住。

## 改动二：运行时——一根"接力棒"式的调度器

编译器把岔路口标好了，真正在岔路口做决定、让 goroutine 排队等待的，是运行时。

这里有个巧妙的复用：Go 1.25 起标准库有个叫 **synctest** 的东西（1.24 时是实验特性，1.25 转正为 `testing/synctest`），专门用来测试并发代码——它能把一组 goroutine 关进一个隔离的"泡泡"（bubble）里，配一个假时钟，还能判断"泡泡里所有 goroutine 是不是都卡住了"。这恰好是 weave 需要的一半能力。weave 就直接站在 synctest 的肩膀上，给 bubble 加了个"受控模式"。

weave 补上的另一半，是一套**接力棒（run token）机制**：

- 整个 bubble 里**只有一根接力棒**，谁拿到棒谁才能跑。
- 一个 goroutine 跑到岔路口（一次内存访问、一次 channel 操作、或显式 `Yield`），它就**把棒交出来**，然后原地等待。
- 交给谁？由上层的探索引擎决定。这就是"在岔路口选一条路"落地的地方。
- 当拿棒的 goroutine 阻塞了（比如等一个空 channel），它同样把棒传给下一个能跑的。**如果没有任何人能接棒——那就是死锁**，weave 当场抓住。

这套设计最漂亮的地方在于：它**几乎没碰 Go 原本的调度主循环**（`schedule`/`findRunnable` 这些主逻辑没动）。weave 主要在两类地方发力：

- **阻塞与死锁"白拿"**：goroutine 本来阻塞就要走 `gopark`、被唤醒就要走 `goready`，weave 只在这几个既有必经之路上插了个"要不要交棒"的判断。串行化和"没人能接棒 = 死锁"都是从这里免费得到的。
- **每个同步操作变成切换点，靠的是标准库里的轻量钩子**：一次**没有竞争**的 `Lock()` 其实是个原子 CAS、根本不阻塞，光靠 park/ready 抓不到它。所以 `chan.go`、`internal/sync/mutex.go`、`sync/waitgroup.go` 里各加了几行 `weaveSchedPoint(...)`：既在这里制造一个调度点，也把"谁对哪个对象做了什么操作"记录下来供上层 DPOR 分析。这些钩子由一个全局标志 `weaveGloballyActive` 的单次读来门控——没在跑 weave 时几乎零成本。

需要强调的是：**要改的是标准库这几处，不是你的代码**。你写的仍然是最普通的 `chan`、`sync.Mutex`——用户侧真正做到零改写。而不在 weave 测试里的普通程序，也只多付那个"在不在受控泡泡里"的分支判断。

还有几个体贴的细节：
- **panic 兜底**：spawn 出来的 goroutine 如果 panic（比如并发 bug 导致的空指针），weave 会捕获它、当作一次"发现的失败"来报告，而不是让整个测试进程直接崩掉。
- **确定性**：weave 内部用一个确定性随机数发生器，让 map 遍历顺序、maphash 种子这些在多次运行间保持一致——不然"复现"就无从谈起。
- **稳定编号**：每个 goroutine 有一个稳定的参与者 id（就是报告里的 `g0`/`g1`），按入组顺序分配，多次运行间一致。

## 改动三：testing 库——探索引擎 + 好用的门面

前两层把"能串行控制、能在岔路口切换"这套机械装置造好了。第三层负责两件事：**怎么聪明地枚举**，以及**给用户一个顺手的 API**。

### 聪明枚举：DPOR

最朴素的枚举是"把每个岔路口的每种选择都试一遍"，但这样组合爆炸，goroutine 一多就跑不完。

weave 用的是 **DPOR（动态偏序规约）**。它的洞察是：**很多不同的顺序其实是等价的**。比如两个 goroutine 各自改各自的变量，谁先谁后结果都一样——这种就没必要两种都试。DPOR 只在**真正会相互影响**的操作对（访问同一块内存、且至少有一个是写）之间去翻转顺序，其余等价的顺序全部跳过。这样能指数级地砍掉冗余，把"跑不完"变成"跑得完"。

（工程上还留了个穷举枚举器，专门用来验证 DPOR 没有漏掉任何结果——两者结果必须一致。）

### 门面 API

对用户来说，这一切被收进一个极简的入口：

```go
func Test(t *testing.T, f func())  // 反复跑 f，枚举交错
func Wait()                        // 等其他 goroutine 都结束（相当于 WaitGroup.Wait）
func Yield()                       // 手动插一个调度点
```

写起来就是普通并发代码，没有任何特殊类型、特殊 channel：

```go
func TestLostUpdate(t *testing.T) {
    weave.Test(t, func() {
        x := 0
        go func() { x = x + 1 }()
        go func() { x = x + 1 }()
        weave.Wait()
        if x != 2 {
            panic("lost update")
        }
    })
}
```

> 有一条重要约定：`f` 会被跑很多遍，所以**所有共享状态都必须建在 `f` 内部**，不能从外面捕获可变变量——否则状态会在多次运行间串味。这也是为什么 `Test` 的闭包故意**不接收 `t`**：用签名提醒你"这里的契约和普通测试不一样"。

## 一次完整的抓捕

跑上面那个 `TestLostUpdate`（带 `-weave`，因为要探查普通 int 上的竞争）：

```
$ go test -weave -run TestLostUpdate
```

weave 探索了几条调度后，找到了那个"两个 goroutine 都读到 0、结果只加了 1"的交错，报告长这样：

```
weave: found failing interleaving after 3 schedule(s):
  goroutines:
    g0: model root
    g1: weaveproto.TestLostUpdate.func1 (weave_test.go:29)
    g2: weaveproto.TestLostUpdate.func1 (weave_test.go:30)
   1: g0 run
   2: g0 write  weave_test.go:28
   ...
   8: g1 read  weave_test.go:29
  10: g2 read  weave_test.go:30
  11: g1 write  weave_test.go:29
  13: g2 write  weave_test.go:30
  15: g0 read  weave_test.go:32
panic: lost update
reproduce with: WEAVE_REPLAY=0.0.0.0.0.0.1.1.2.2.1.0.2.0.0 go test -run TestLostUpdate
```

几个看点：

- **goroutine 图例**：`g1`、`g2` 不再是冷冰冰的编号，而是标出了它们各自在 `weave_test.go:29` / `:30` 被 `go` 语句创建的位置。一眼就知道谁是谁。
- **逐步交错**：清清楚楚地看到 `g1 read` → `g2 read`（两个都读到了旧值 0）→ 各自 write，丢更新就是这么发生的。
- **复现种子**：把那串 `WEAVE_REPLAY=...` 设上，就能**确定性地重放这一模一样的交错**——heisenbug 从此变成必现 bug。

## 和 `-race` 到底啥关系

一句话：**互补，不是竞争。**

| | `-race` | `weave` |
|---|---|---|
| 工作方式 | 旁观一次真实执行 | 接管调度、系统枚举很多次 |
| 找什么 | 数据竞争（漏加同步） | 调度相关的逻辑 bug：死锁、丢更新、不变量破坏、泄漏 |
| 能不能靠谱地找到 | 取决于这次调度的运气（可能假阴性） | 系统覆盖，不靠运气 |
| 规模 | 能跑整个程序、真并行、上生产测试 | 适合关键并发单元的穷尽验证 |

一段**完全没有数据竞争**（锁都加对了）的代码，仍然可能死锁或丢信号——`-race` 永远报不出来，weave 能。反过来，大型程序的整体竞争排查，还得靠 `-race`。各司其职。

## FAQ

**Q：weave 会不会把我的代码改慢 / 需要我改代码？**
不需要改代码。你写的是最普通的 `go func()`、`sync.Mutex`、`chan`、`int`。channel/mutex 类的测试连 `-weave` flag 都不用加；只有要探查普通变量上的数据竞争时，才需要 `-weave` 让编译器插桩。至于速度：非 weave 的普通程序只多一个几乎免费的分支判断。

**Q：goroutine 一多，会不会组合爆炸跑不完？**
这正是 DPOR 要解决的——它只在真正相互影响的操作间翻转顺序，跳过所有等价交错，能指数级剪枝。即便如此，超大状态空间仍可能很慢，所以报告会告诉你探索了多少条调度；后续还可以加"抢占次数上界"之类的兜底策略。weave 更适合"小而关键"的并发单元，而不是给整个大程序做穷尽。

**Q：我的业务代码里有全局变量 / 单例，用例间接引用到了，怎么办？**
先分清踩的是哪种雷。（1）**只读配置**（init 设一次不改）：不用管。（2）**可变全局状态**（计数器、全局缓存、全局 map）：会在多次运行间残留、互相污染，办法是在 `f` 开头重置成初值，或更好——重构成依赖注入，在 `f` 内部把它 new 出来传进去。（3）**背后有后台 goroutine 或真 I/O 的单例**（连接池、定时器、metrics 上报）：最麻烦——这些 goroutine 生在"泡泡之外"，weave 根本管不到，会真并行地插手，既破坏复现又让分析出现盲区。对这种**必须换成在 `f` 内构造的 fake/stub**（留一个 interface 接缝）。另外注意 `sync.Once` 守护的初始化：第一遍就 fire 了，第二遍不会再跑，也需要可重置的接缝。判断自己踩雷的信号：同一 seed 复现不出、多次运行结果时好时坏、或报告图例里冒出你没显式 `go` 出来的 goroutine。核心原则一句话：**weave 要求每一遍都能从零重演。**

**Q：报告里的种子（seed）会一直有效吗？**
在代码不变的前提下有效。种子本质是"每个岔路口选了第几条路"的序列，只要模型除了调度之外是确定的（不依赖真实时间、真随机数、map 遍历顺序），重放就能精确复现。**一旦你改了被测代码，种子通常就失效了**——因为岔路口的结构变了。

**Q：为什么 `weave.Test` 的闭包不接收 `t`，还要求状态建在内部？**
因为 `f` 会被反复执行很多遍。如果它捕获了外部的可变变量，状态就会在多次运行之间残留、串味，导致结果不可信。不传 `t`、要求自包含，是用 API 的形状来**强制**这个"可重跑"的契约，避免误用。

**Q：能同时开 `-weave` 和 `-race` 吗？**
不能，会直接报错。它们抢用编译器里同一条内存插桩流水线，凑一起会让 weave 被悄悄丢掉、结果不可信，所以干脆在 flag 校验阶段就拦住。要查数据竞争用 `-race`，要穷尽交错用 `-weave`，分开跑。

**Q：weave 能替代 `-race` 吗？**
在它的受控泡泡里，weave 其实掌握了完整的先后关系（happens-before），理论上可以顺带把数据竞争也报出来，而且是"跨所有已探索交错"地报，比跑一遍的 `-race` 更强。但泡泡外——整个程序、真实多核并行、大型集成测试——仍然是 `-race` 的主场，weave 扛不动那个规模。所以定位是互补。

**Q：它和 Rust 的 loom 有什么不同？**
思路同源（都源自 CHESS 那套系统化交错探索），但 loom 强制你把 `std::sync` 换成 `loom::sync`，这是很重的工程负担。weave 的目标是**零改写**：靠复用运行时的 synctest 泡泡 + 类比 `-race` 的编译器插桩，让**未经修改的、用真实 `chan`/`sync.Mutex` 的代码**直接被探索。

---

*weave 仍在演进中。它把"并发 bug 靠运气撞"这件事，变成了"系统地把每种可能都试一遍"。下次再遇到那个凌晨两点的 heisenbug，也许你需要的不是更多日志，而是一次 `go test -weave`。*
